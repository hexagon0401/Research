# v2.4.2 — 지구본·경로 왜곡 수정과 스크롤 최적화

2026-11-02. 기준 v2.4.1 `4dea481`. 앱 루트 `v1.1.0/`, Vercel Hobby·Supabase Free와 기존 연구·공개 API를 유지한다.

## 원인과 수정

- 기업→국가 SVG의 `preserveAspectRatio="none"`이 지구본을 비균등하게 늘렸다. 수정 전 화면 배율 비는 1440×1000에서 0.6568, 390×844에서 1.1480이었다. 모든 애니메이션 SVG와 HTML 라벨·확대 보기를 같은 720×520 종횡비 유지 프레임으로 통일했다.
- 지도 곡선의 제어점이 항상 두 지점의 위쪽에 있었다. 미얀마·캄보디아처럼 남북 방향의 지점에서는 실제 역행이 발생했다. 제어점을 중간점의 수직 방향으로 거리의 18%(최대 60 원본 단위)만큼 이동하여 경로가 출발 쪽으로 되돌아가지 않게 했다.
- 비확대 선 굵기와 정규화 dash를 같은 SVG path에 적용하면 확대 시 선이 조각났다. 선 그리기는 카메라와 함께 확대되는 별도 마스크가 담당하고, 실제 선은 일정한 굵기를 유지한다. 확대 대화상자는 마스크 ID·참조를 재매핑해 원래 도식과 독립된 정적 복사본을 유지한다.
- 이동점은 경로의 로컬 좌표에서 계산한다. 지점 반지름 4px·이동점 3px과 테두리를 카메라 확대와 분리했다. 원본과 같은 지리 좌표를 사용하며, 경로가 완성된 뒤 지역을 확대한다. 0~10% 구도→10~55% 경로→55~85% 확대→85~100% 읽기 순서다.
- 기존 CSS sticky와 연구 순서를 유지한다. 18개 논지 주소, 13개 전문, 973개 대응 문단과 PDF·API·백엔드는 보존한다. 새로운 수송 사실이나 연구 결과는 추가하지 않았다.

## 스크롤 처리

엔진 준비 후 ScrollTrigger만 진행을 계산하고 native 스크롤 계산은 로딩 전·실패·모션 감소 상황의 대체 동작으로 남긴다. 레이아웃 무효화는 한 프레임으로 묶고, 장면 경계가 바뀌면 트리거 범위도 갱신한다.

문단 위치·경로 길이·DOM 참조를 캐시한다. 현재 단계·카메라가 바뀔 때만 필요한 속성을 갱신한다. 현재 DOM에서 사용하지 않는 메인 전체의 상속 CSS 변수 갱신을 제거하고, 첫 지구본의 작은 이동은 그 요소에만 적용한다. 더 이상 사용하지 않는 MotionPathPlugin 로딩도 제거했다.

## 측정과 검증

동일한 Linux Chromium·Node.js 24.19.0·Next.js 16.4.2 운영 빌드 조건에서 비교한다. 화면은 1440×1000, 1440×600, 768×1024, 390×844를 기본으로 사용했다. [수정 전 수치](validation/v2.4.2-before-motion.json)와 최종 비교 기록을 보관한다.

- 운영 빌드·타입·29개 단위/콘텐츠 검사, 원문 보존·번역 지문·PDF 13개 해시·공개 API/백엔드 잠금 검사 통과.
- 전체 브라우저 매트릭스 **197개 통과·31개 환경 조건부 제외·실패 0**(228항목, 5.0분). 이후 화면 밖 렌더링 지연 보완에 관련된 데스크톱/모바일 회귀 **34개 추가 통과·2개 조건부 제외·실패 0**. 최종 빌드에서는 아래 100개 좌표 표본과 성능을 다시 측정했다.
- 12개 도식의 다섯 진행 위치, 320~1920px·낮은 화면·200% CSS 확대·한영 전환, 정/역방향 휠·키보드, 원문 왕복·직접 문단 주소, 확대 대화상자·마스크 복사, 모션 감소·엔진 실패·No-JS, 자료실·큰 PDF 다운로드 해시를 검사했다.
- 최종 100개 수치 표본 중 SVG 배율 비를 측정한 40개는 모두 **1:1**이었다. 곡선 역행은 **0개**, 진행 중 경로 36개 표본의 화면 이탈은 **0개**였다. 이동점과 경로의 2px 이내 정렬 및 3px 반지름은 별도 브라우저 검사로 확인했다. 완료 후 지역 확대의 의도된 경로 잘림은 이탈 실패에 포함하지 않는다.
- Chromium CDP 터치 드래그에서 진행률 0.3201→0.3820, 고정 그림 70~327.7px(390×844)을 확인했다. 한국어 전환 후에도 캄보디아 단계 4와 그림 위치가 유지됐다.
- 최종 표본 100개 화면을 로컬 `.local/v242/final/`에 저장했다. 대표 [수정 전 지구본](validation/v2.4.2-globe-before.png)과 [수정 후 지구본](validation/v2.4.2-globe-after.png)을 함께 보관한다.

### 스크롤 비용

뷰포트마다 같은 50회 native wheel 입력을 3회 실행한 중앙값이다. 초기화·스크린샷 촬영은 측정 구간에서 제외했다. [수정 전](validation/v2.4.2-before-motion.json)·[수정 후](validation/v2.4.2-after-motion.json)에는 개별 회차도 보관한다.

| 화면      | 스크립트 시간 전→후 | 레이아웃 시간 전→후 | 스타일 계산 전→후 | 프레임 간격 p95 전→후 |
| --------- | ------------------- | ------------------- | ----------------- | --------------------- |
| 1440×1000 | 55.9→28.9ms         | 79.8→23.2ms         | 1122.6→16.7ms     | 33.4→16.7ms           |
| 1440×600  | 54.4→28.4ms         | 63.9→23.4ms         | 1137.9→16.2ms     | 16.8→16.8ms           |
| 768×1024  | 51.9→26.0ms         | 56.8→22.2ms         | 1071.2→15.3ms     | 16.8→16.8ms           |
| 390×844   | 48.9→26.0ms         | 54.4→18.9ms         | 1099.6→12.8ms     | 16.8→16.7ms           |

이 시나리오에서 스타일 계산은 약 **98.5~98.8% 감소**했다. 최종 12회 스크롤 측정 중 50ms 이상 긴 작업은 관측되지 않았고, 정지 후 500ms 표본에서는 도식 속성 변이·시각 변화가 모두 0이었다. 엔진 내부의 모든 rAF 콜백이 사라졌다는 주장은 아니다. 화면 크기가 좁은 데스크톱 휠 표본과 실제 휴대전화 성능은 구분한다.

### 초기 로딩

Lighthouse 13.5.0 기본 모바일·시뮬레이션 제한으로 각 빌드를 3회 측정했다. [수정 전 결과](validation/v2.4.2-before-lighthouse.json)와 [최종 결과](validation/v2.4.2-after-lighthouse.json)를 보관한다.

| 빌드           | 회차별 성능  | 성능 중앙값 | 접근성 | 권장사항 |
| -------------- | ------------ | ----------- | ------ | -------- |
| 수정 전 v2.4.1 | 88 / 90 / 88 | **88**      | 100    | 100      |
| 최종 v2.4.2    | 92 / 92 / 91 | **92**      | 100    | 100      |

최종 LCP 중앙값은 약 3.18초, TBT는 120.5ms, CLS는 0, 초기 전송량은 약 455KB였다. 프레임 도입 중간 빌드에서 [중앙값 81점](validation/v2.4.2-eager-lighthouse.json)이 나와 화면 밖 SVG·라벨 초기화를 지연한 뒤 최종 빌드를 새로 측정했다. 좋은 회차만 골라 중앙값을 계산하지 않았다.

**초기 로딩 목표 95점에는 미달**한다. 기존 `audit:performance` 기준을 유지하므로 해당 명령은 실패 종료한다. 기능·접근성 검사와 목표 성능 미달을 구분해 기록한다. 이 로컬 결과는 운영 현장의 Core Web Vitals를 보장하지 않는다.

### 운영 반영

## 재현과 배포

```sh
npm ci
npm test
npm run build
npm run typecheck
npm run audit:readings
npm run audit:preservation
npm run format:check
CHROME_PATH=/usr/bin/chromium E2E_BASE_URL=http://127.0.0.1:3000 npm run test:e2e
MEASURE_URL=http://127.0.0.1:3000 MEASURE_OUTPUT=.local/v242/after MEASURE_CAPTURES=all node scripts/measure-motion.mjs
CHROME_PATH=/usr/bin/chromium AUDIT_URL=http://127.0.0.1:3000 npm run audit:performance
```

운영 서버는 별도 터미널에서 `npm run start`로 실행한다. 성능 측정은 다른 브라우저 회귀 작업 종료 후 실행한다. Lighthouse의 기존 95점 기준은 낮추지 않는다. 스크롤 최적화가 이번 우선 목표이며, 초기 로딩 목표의 미달 여부는 실제 수치대로 기록한다.

검증 후 main·v2.4.2 태그를 GitHub에 푸시하고 운영 주소의 반영을 별도로 확인한다. 배포 문제가 발생하면 v2.4.1을 다시 배포할 수 있다. Linux Chromium의 터치·확대 에뮬레이션은 실제 iOS Safari 기기 검사를 대신하지 않는다.
